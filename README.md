# Autopia

Autopia empirically tests read-only HTTP APIs that ship an OpenAPI spec, discovers how they
**actually** behave, verifies every finding by reproducing it, and stores the result as a
versioned, queryable knowledge base that any AI agent can consult over MCP.

It is the MVP of the "Discrimen Compendium" described in `docs/compendium-spec.txt`
(the blueprint) and `docs/compendium-stack.txt` (stack choices). Read the spec's glossary
first; the code uses those exact terms.

## The pipeline

```
discover -> exercise -> aggregate -> cross-ref -> verify -> write (+ diff)
 spec       TRIALS      rules +      spec +       evidence   CLAIMS
 fetch,     (no LLM)    one LLM      self-        check +    + DIFFS
 hash                   pass         consistency  reproduce
```

- **Trials** are pinned requests generated by the **battery** (`src/worker/battery`), a
  deterministic catalogue of edge cases (omit required, wrong type, nulls, boundaries,
  unknown fields, bad auth, pagination edges, duplicates, wrong content type, trailing slash,
  HEAD). No randomness anywhere, so two runs produce identical trial inputs.
- **Claims** come from two sources: deterministic **rules** over the trials (free, no model),
  and **one** batched LLM pass for open-ended discovery. The LLM output is validated with
  ajv against `src/schemas/claim.schema.json`; invalid objects are discarded.
- **Verification** is the product: every claim cites trial ids and the status each showed.
  The evidence check is mechanical; reproduction re-runs the exact inputs and compares a
  normalized response **signature** (status, body kind, JSON shape, error message), never
  raw bytes, so live data can change without breaking reproduction. Non-reproducing claims
  are discarded. Stored claims are always `verified = true`.
- **Divergences** are claims that contradict a documented fact (required flag, type, enum,
  range). The money view. Silence in the spec is never a divergence: a rule the API enforces
  that the spec never states (parameters that must be sent together, implicit defaults) is
  stored under its own kind, `undocumented_constraint`, so the strict flag stays
  machine-checkable and the softer findings stay queryable.
- **Claim kinds:** `required`, `type`, `auth`, `pagination`, `error_behavior`,
  `undocumented_constraint`, `undocumented`, `other`.
- **Sibling comparison.** Tools that share a `category` are compared probe by probe: the
  same rule on the same parameter name with the opposite verdict (one accepts, one rejects)
  marks the claim `divergence_type = sibling` with a note naming the other tool. Only rules
  claims take part; LLM claims are too free-form to line up across tools.
- **Diffs** compare claim sets across tool versions by stable `claim_key`.

## Quick start

```bash
npm install
npm run autopia -- run targets/open-meteo-forecast.json     # full pipeline, rules only
npm run autopia -- claims open-meteo-forecast --divergences
npm run autopia -- search "is latitude required"
npm test
```

To enable the LLM pass, copy `.env.example` to `.env` and set `ANTHROPIC_API_KEY`.
Without a key the pipeline runs rules-only and says so.

### Serving the compendium

```bash
npm run mcp          # MCP server over stdio (register in Claude Code / any MCP client)
npm run mcp:http     # the same server over Streamable HTTP at http://localhost:4200/mcp
npm run dashboard    # read-only dashboard at http://localhost:4100
```

Register the stdio server with a client as `npx tsx <repo>/src/server/mcp.ts`, or point an
HTTP-capable client at `/mcp` on the HTTP server (`GET /healthz` for liveness).
Tools: `list_tools`, `list_versions`, `get_tool_knowledge`, `get_divergences`,
`search_claims`, `get_version_diff`, and `get_tool_docs`, which returns a Markdown behavior
sheet generated from the verified claims (spec contradictions first, then sibling
differences, undocumented rules, per-endpoint behavior), every line citing its trial ids.
The same sheet is `npm run autopia -- docs <tool>` and `GET /api/tools/<tool>/docs` on the
dashboard. Every response carries the evidence trials.

### Keeping it current (automation)

```bash
npm run run-all      # run every targets/*.json in sequence, one summary line per tool
```

`run-all` re-fetches each spec, creates a new tool version when the spec hash changes,
re-exercises, re-verifies, and computes the diff against the previous version automatically.
It exits non-zero if any target fails.

**Cost controls.** The model pass is the only cost that scales with targets, so the schedule
splits in two: `run-all --no-llm` nightly (free) and `run-all` with the LLM weekly. Rules-only
runs do not lose the model's claims: every run **carries forward** the previous run's LLM
claims as candidates, remapped to tonight's trials by endpoint and probe, and sends them
through the same evidence check and reproduction as everything else. A carried claim whose
behavior changed fails and is dropped. **Retention:** `--prune-days N` (or `autopia prune N`)
deletes runs older than N days except the latest finished run of each version and any run a
diff cites, so the database stays small without losing anything queryable. `--dry-run` reports
without deleting. Schedule it with whatever you already have:

- Windows: Task Scheduler, action `npm run run-all` in the repo folder.
- Linux/macOS: a cron line such as `0 3 * * * cd /path/to/autopia && npm run run-all >> runs.log`.
- Hosted: the same command as a scheduled job on Fly.io, Railway, or Render, with
  `DATABASE_URL` pointing at a managed Postgres so the MCP server can stay up while the
  worker runs (the embedded database allows only one process at a time).

**PGlite caveat:** the default database is an embedded Postgres (PGlite) under `data/pglite`
and only one process can open it at a time. Stop the worker before starting the MCP server
or dashboard. Set `DATABASE_URL` to a real Postgres to lift that limit (same schema, no code
change).

## Hosting: managed Postgres + the HTTP MCP server

The embedded database is for one laptop. A hosted compendium uses a managed Postgres so the
worker and the server can run at the same time, and runs the HTTP MCP server somewhere always on.
The code path is identical: `DATABASE_URL` switches drivers, migrations apply on connect, and
`tests/integration/postgres-path.test.ts` exercises it over the real Postgres wire protocol.

**1. Database (Neon or Supabase, both include pgvector).** Create a project, copy the
connection string, and move the existing compendium across:

```bash
npx tsx scripts/db-export.ts data/export.json
```

```bash
DATABASE_URL="postgres://..." npx tsx scripts/db-import.ts data/export.json
```

Import preserves ids, skips rows that already exist, and resets the sequences, so it is safe
to re-run. Put the same `DATABASE_URL` in `.env` and every command on the laptop now talks to
the hosted database.

**2a. Server on Render (free tier, no card).** `render.yaml` is a Blueprint. Push the repo to
GitHub, then in Render: New -> Blueprint -> select the repo. It builds the Dockerfile, asks for
`DATABASE_URL` (paste the Neon direct string) and generates `AUTOPIA_MCP_TOKEN` (copy it from the
service's Environment tab). Free services sleep after ~15 idle minutes and wake on the first
request, so expect a slow first call. The nightly refresh runs as a free GitHub Actions
schedule (`.github/workflows/run-all.yml`) using repository secrets `DATABASE_URL` and
`ANTHROPIC_API_KEY`; it can also be triggered by hand from the Actions tab.

**2b. Server on Fly.io (paid account, always-on).** `fly.toml` and the `Dockerfile` are in the repo. One time:

```bash
fly launch --copy-config --no-deploy
```

```bash
fly secrets set DATABASE_URL="postgres://..." AUTOPIA_MCP_TOKEN="$(openssl rand -hex 24)"
```

```bash
fly deploy
```

The server listens on `/mcp` with `GET /healthz` for the platform check. With
`AUTOPIA_MCP_TOKEN` set, every `/mcp` request needs `Authorization: Bearer <token>`; unset, the
endpoint is open and the server logs a warning. The image also contains the worker: run it as a
scheduled machine or by hand with `fly ssh console -C "npm run run-all"`, with
`ANTHROPIC_API_KEY` set as a secret if the LLM pass should run there. Railway and Render work
the same way from the same `Dockerfile`.

## CLI

| Command | What it does |
|---|---|
| `run <target.json> [--no-llm] [--max-trials N] [--no-reproduce]` | full pipeline on one target |
| `plan <target.json>` | print the trial plan without sending anything |
| `tools`, `versions <tool>`, `runs <tool>` | catalogue |
| `claims <tool> [--divergences] [--version ID] [--json]` | verified claims with evidence |
| `search "<question>" [--tool NAME]` | text search over claims |
| `diff <tool> <fromVersionId> <toVersionId>` | changelog between versions |
| `trial <id>` | one trial in full |
| `compare-runs <tool>` | determinism check across the last two runs |

`AUTOPIA_LOG=debug` prints every trial and every verification decision.

## Adding a target

Create `targets/<name>.json`:

```json
{
  "name": "my-api",
  "category": "weather",
  "spec_url": "https://example.com/openapi.yml",
  "baseline": { "/v1/path": { "required_param": "known good value" } },
  "optional_values": { "/v1/path": { "optional_param": "known good value" } },
  "headers": { "x-api-key": "..." },
  "rate": { "concurrency": 2, "min_interval_ms": 150 },
  "max_trials": 500
}
```

Scope rule (v1): public, read-only, OpenAPI 3.x, no auth beyond a simple key. If a target
lacks a formal spec or has side effects, it is out of scope; `discover` stops with an error.

## Testing

- `npm run test:unit` — one file per stage under `tests/unit`: spec parsing, battery,
  signature, HTTP executor (with fake fetch), rules, cross-ref, verify, diff.
- `npm run test:integration` — the real pipeline against a **mock API with planted quirks**
  (`tests/mock-api/server.ts`), on a throwaway database: finds the planted divergences,
  stores only verified claims, is deterministic across runs, diffs a second version, and
  exercises the LLM path with a fake adapter. A second file spawns the real MCP server and
  calls every tool through an MCP client.
- `npm run mock-api` starts the mock API by hand for manual poking.

## Layout

```
docs/               spec + stack docs
targets/            one JSON per API under study
drizzle/            generated SQL migrations (npm run db:generate after editing schema.ts)
src/db/             schema.ts (source of truth), client.ts (PGlite or Postgres), queries.ts
src/worker/         pipeline stages: discover, exercise, aggregate/{rules,llm}, crossref,
                    verify, write, diff, pipeline.ts, cli.ts; battery/ ; signature, http
src/llm/            provider adapter (worker only, never the server)
src/schemas/        claim.schema.json
src/server/mcp.ts   MCP server
src/dashboard/      Express + static page
tests/              unit, integration, mock-api, helpers
```
